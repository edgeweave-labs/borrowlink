# BorrowLink —— 向手邊有網路的裝置借一條路

版本：draft-1（尚未實作，尚未在任何硬體上驗證）
日期：2026-08-19

一台沒有自己的網路的隨身裝置，對空中喊一聲「我有東西要送」，附近願意幫忙且有網路的裝置接手，把那一條 request 走完，然後散場。

適用於這個 workspace 底下所有 ESP32 隨身板，不綁定任何一塊板子的硬體。

---

## 1. 這份協議要解決的問題

隨身裝置沒有 SIM，離開已知的 Wi-Fi 就沒有網路。但身邊幾乎總有一台**已經連著網路**的東西——手機、筆電、桌機。

借用它的網路，不能靠讓裝置加入對方的網路（公司網路可能禁止私人設備），也不能靠接線（要隨身）。剩下的只有一條短距離無線鏈路，而在 ESP32-S3 上那只能是 BLE。

**這不是 IP 層的橋接。** 裝置不會取得 IP 位址，不會出現在對方的網路上。它把一個完整的請求交給對方，對方用自己的身分送出去，再把結果交回來。從網路的角度看，流量是那台 gateway 發的，跟它平常的流量沒有分別。

---

## 2. 三個不可讓步的前提

這三條決定了底下所有設計。任何與它們衝突的做法都不採用。

**一、平時完全不耗電。** 裝置不用時 BLE 徹底關閉，不是低頻掃描，不是低功耗廣播——關閉。

**二、要用才連，用完就斷。** 沒有常駐連線，沒有保活。一次交易結束，鏈路就拆掉。

**三、穩定性優先於速度。** 一條慢但走得完的路，勝過一條快但一半機率斷在中間的路。

---

## 3. 誰廣播、誰監聽

**裝置廣播，gateway 監聽。**

這與智慧手錶相反。手錶是 peripheral 且持續廣播，因為它必須隨時可被找到——通知隨時會來。這裡不需要那個：只有裝置自己知道它什麼時候有話要說。

功耗是決定性的理由。BLE 廣播是短脈衝發射，間隔數百毫秒，平均電流在數十 µA 的量級；掃描是持續接收，平均電流在 10–20 mA 的量級。兩者相差一到兩個數量級（**一般公開數據，未在本 workspace 的任何板子上量測**）。

把耗電的那一端放在插電的裝置上，是這個協議唯一能做的正確選擇。

```
裝置                                gateway（電腦／手機／另一台 ESP32）
────                                ──────────────────────────────
平時：BLE 關閉，0 mA                 平時：掃描指定的 service UUID

有東西要送
  └─ 開 BLE，開始廣播 ─────────────→ 收到
                                       └─ 連線 ←─────────────┐
  接受連線（僅限已配對）←──────────────────────────────────┘
  送出 request ────────────────────→ 用自己的網路送出去
  收到 response ←──────────────────── 把結果送回
  斷線 ──────────────────────────────→
  關 BLE，回到 0 mA
```

### 冗餘是這個選擇的副產品

所有 gateway 監聽**同一個 service UUID**。一次廣播，所有在監聽的都收到，誰先連上誰接手。

電腦沒開機，手機接。兩個都在，先舉手的接。這不需要任何協議支援，也不需要裝置維護一張 gateway 清單——它是「裝置廣播」這個決定自己帶來的。

### 這不是 mesh，刻意不是

BLE Mesh 是多跳與 flooding，要求節點常開接收。那與前提一直接衝突：一台 BLE 關著的裝置聽不到任何東西，不可能替別人中繼。

本協議是**單跳**。多跳的欄位有預留（見 §5 的 `ttl`），但機制不存在，現在也不該存在——多跳需要至少一個常開的節點，而那是另一個決定，不是這一份文件的範圍。

## 4. 兩個階段，中間沒有第三個

**階段一：發現。** 廣播、無連線、不保證有人回應、可能多人回應。形狀等同 DHCP DISCOVER：喊一聲、誰能幫忙誰 OFFER、挑一個、完成交易、沒人回應就退避重試。

**階段二：傳輸。** 建立連線之後，BLE 的 link layer 保證送達與順序，L2CAP 有流量控制。

### 第二階段不需要自己做可靠性

這是最容易做錯、也最貴的地方。

發現階段那種「喊出去不知道誰收到」的感覺，很容易讓人以為整條路都是不可靠的，於是在上面疊序號、ACK、重傳、逾時視窗、亂序重組。

**那些全部不要寫。** BLE 連線建立之後，資料要嘛完整按序到達，要嘛連線斷掉——而連線斷掉是一個明確的事件，不是要靠逾時去猜的沉默。

分塊（§7）只是為了繞過 characteristic 的長度上限，**不是為了可靠性**。這兩件事長得像，工作量差十倍。

## 5. 發現階段：廣播內容

BLE legacy advertising，31 位元組。刻意不用 extended advertising——相容性更廣、更省電，而且要放的東西本來就塞得下。

Service Data 內容，共 6 位元組：

| 位移 | 欄位 | 大小 | 說明 |
|---|---|---|---|
| 0 | `version` | 1 | 協議版本。本文件為 `0x01`。 |
| 1 | `intent` | 1 | 這次廣播想做什麼。見下表。 |
| 2 | `xid` | 2 | Transaction ID，每次新的請求隨機產生。 |
| 4 | `attempt` | 1 | 這是第幾次嘗試同一個 `xid`，從 0 開始。 |
| 5 | `ttl` | 1 | 允許的剩餘跳數。單跳一律為 0。 |

`intent` 的值：

| 值 | 意義 |
|---|---|
| `0x01` | 借網：幫我把一個 HTTP 請求送出去 |
| 其他 | 保留 |

### node ID 不另外放

BLE 廣播本來就帶 device address，那就是 node ID，不需要重複佔位元組。使用 resolvable private address 時，已配對的 gateway 解得出來，未配對的解不出來——這正是想要的行為。

### 四個欄位裡有三個現在就有用

| 欄位 | 現在（單跳）的用途 | 未來（多跳）的用途 |
|---|---|---|
| device address | 配對白名單要識別對方 | 定址「這是誰的請求」 |
| `xid` | 重試時分辨回應對應哪一次請求 | 端到端對應，跨越中繼 |
| `intent` | 借網 vs 其他用途 | 「幫我轉發」也是一種 intent |
| `ttl` | —— | 防止多跳無限迴圈 |

只有 `ttl` 是純預留，一個位元組。它換掉的是「未來要做中繼就得改封包格式、破壞相容性」。

**留欄位，不留機制。** 現在不要寫 routing table、不要做 neighbor discovery、不要分 Low Power Node 與 Friend Node 角色。那些在有第一個常開節點之前沒有意義。

### attempt 讓失敗的 gateway 讓路

先連上的不保證是最能辦事的那個——手機在弱訊號區也可能搶先舉手然後辦不成。

規則：**gateway 收到 `attempt > 0` 的廣播，若自己剛對同一個 device address 與 `xid` 失敗過，必須延遲數秒才允許回應。**

這讓第二輪自然輪到別人。約二十行邏輯，換到真正的多路徑，而不是「有多個 gateway 但每次都同一個接」。

`attempt` 是 8 位元，溢位前早就該放棄了；上層自己決定放棄的次數。

## 6. 配對是必要的，不是選項

**gateway 看得到 bearer token。**

它代發 HTTPS，所以憑證必須明文交給它。裝置到最終伺服器之間沒有端到端加密，gateway 就是中間人。

因此：

- 裝置**只接受已配對（bonded）的 central 連線**，未配對的連線立即斷開。
- 配對使用 LE Secure Connections，鏈路加密。
- 配對是一次性的、需要人在場的動作，不能自動完成。

沒有這一條，任何人在你附近監聽那個 service UUID 就能收走 token。這不是縱深防禦的加分項，是這個協議能不能存在的前提。

## 7. 傳輸階段：GATT 佈局

語意參考藍牙 SIG 的 HTTP Proxy Service（`0x1823`）——URI、headers、body、method、status code 這組拆法是它定義的，直接沿用，不重新發明。

**但不使用 HPS 本身。** HPS 的 entity body 受限於單一 characteristic 的 512 位元組，且規格沒有定義分塊；而本協議要送的東西可以到數十 KB（例如一段壓縮後的語音）。差三個數量級，補不上去。

三個 characteristic：

| Characteristic | 屬性 | 用途 |
|---|---|---|
| `Request` | Write | 裝置寫入請求，分塊 |
| `Response` | Notify | gateway 回傳結果，分塊 |
| `Control` | Notify | gateway 回報狀態，見 §8 |

### 分塊格式

`Request` 與 `Response` 使用同一種分塊標頭：

| 位移 | 欄位 | 大小 | 說明 |
|---|---|---|---|
| 0 | `seq` | 2 | 從 0 遞增 |
| 2 | `flags` | 1 | bit0：這是最後一塊 |
| 3 | `payload` | 其餘 | 內容 |

每塊的大小上限由協商後的 ATT MTU 決定，`payload` 最多 `MTU - 3 - 3` 位元組。

`seq` 的存在不是為了偵測遺失或亂序（§4：那由 BLE 保證），而是讓接收端在組裝時能斷言自己的狀態沒有跑掉。**收到不連續的 `seq` 是程式錯誤，不是網路狀況**——應當中止整筆交易並回報，而不是進入重組邏輯。

### 請求本體

第一塊的 `payload` 起始是一個請求標頭，其後接 body：

```
method   1 byte    0x01 GET, 0x02 POST
url_len  2 bytes
url      url_len bytes, UTF-8, 不含 NUL
hdr_len  2 bytes
headers  hdr_len bytes, 以 \n 分隔的 "Name: value"
body     其餘全部
```

回應本體：

```
status   2 bytes   HTTP status code
body     其餘全部
```

### 先用 Write With Response

每一塊都等確認，簡單且不需要應用層背壓。

代價是速度：一塊一個往返，以 15 ms 的 connection interval 估，50 KB 分成一百塊約需一秒半（**推算，未量測**）。

Write Without Response 加滑動視窗會更快，L2CAP CoC（自帶流量控制）更快。兩者都是**優化路徑，不是起點**。特別是 L2CAP CoC 有一個實務代價：Python 的 `bleak` 不支援，走那條就等於每個 gateway 平台都要寫原生程式，而那正是這份協議想避免的重複。

## 8. gateway 必須說出它辦不到

**沉默不是合法的失敗方式。**

一個接了單卻不出聲的 gateway，會把三秒的失敗變成三十秒的逾時，並且在那段時間裡擋住其他本來可以成功的 gateway。這是這份協議裡穩定性最脆弱的一點。

`Control` characteristic 上的狀態碼：

| 值 | 意義 | 裝置該怎麼做 |
|---|---|---|
| `0x00` | 已接手，處理中 | 繼續等 |
| `0x01` | 完成，`Response` 已送完 | 收下，斷線 |
| `0x10` | 我沒有網路 | 斷線，`attempt + 1` 重新廣播 |
| `0x11` | 上游回了錯誤（後接 2 位元組 HTTP status） | 交給上層判斷；重試多半沒用 |
| `0x12` | 上游逾時 | 斷線，`attempt + 1` 重新廣播 |
| `0x13` | 我拒絕代發這個請求 | 斷線，不要對同一個 gateway 重試 |

`0x10` 與 `0x11` 的分別是重點：前者是「這條路不通」，後者是「路通了但對面說不行」。只有前者值得換一個 gateway 再試。

## 9. 選路與能量：便宜的先問

裝置身上可能有兩條路——BLE gateway 與 Wi-Fi。挑錯不只是慢，是白白花掉電。

### 探測成本差三個數量級

粗估，**全部是推算，未量測**：

| 動作 | 電流量級 | 時間 | 能量 |
|---|---|---|---|
| BLE 廣播探路 | ~50 µA | 3 秒 | ~0.00004 mAh |
| Wi-Fi 全頻 scan | ~120 mA | 2 秒 | ~0.067 mAh |

Wi-Fi 探一次路，約等於 BLE 探一千多次。

這個差距來自 §3 的角色分配：裝置**不需要知道**有沒有 gateway，它只要喊一聲然後等。三秒沒人連就是沒有，而喊那一聲幾乎不花錢。Wi-Fi 沒有這種免費的問法——要知道 SSID 在不在，就得把收音機打開掃。

### Wi-Fi 不是首選，這一點與直覺相反

Wi-Fi 本來勝在頻寬。但當 payload 已經被壓到數十 KB（例如 ADR-0015 之後的語音），BLE 分塊約一秒半就送得完，**頻寬優勢在這個尺寸下不存在**。

Wi-Fi 剩下的唯一用途，是 BLE 找不到人的時候。

### 順序：便宜 → 貴 → 便宜

```
階段 1   BLE 廣播 2–3 秒                    幾乎免費
         有人接 → 走完，結束

階段 2   Wi-Fi scan（優先掃記憶中的 channel）  唯一貴的一步
         有已知 SSID → 關聯 → 結束

階段 3   BLE 廣播延長至數十秒                 幾乎免費
         涵蓋手機在背景被節流的慢路徑

階段 4   放棄，回報上層
```

貴的那一步夾在中間：便宜的問法先問完，真的沒人才付那筆錢。

### 貴的那一步還能再壓一個數量級

`esp_wifi_scan_start` 可以**指定 SSID 與 channel**，不必全頻掃。

把上次成功的 channel 存進非揮發性儲存，下次只掃那一個 channel——約 100–200 ms，而不是兩秒。

記憶只用在 Wi-Fi 這一側。BLE 那側不需要記憶，因為探測本來就免費，不需要靠記憶去避免一件不花錢的事。

### gateway 不省電，價值在縮短階段 1

gateway 是插電的或電池很大的，讓它把成本吃下來：

- **以 100% duty cycle 掃描。** 裝置的廣播一發出就被聽到，不必等下一個掃描窗口。
- **收到就連，連線前不做任何判斷。** 要不要接、能不能辦，等連上之後在 `Control` 上回報（§8 的 `0x10`）。把判斷放在連線後，不放在連線前。

這兩件事讓階段 1 的窗口可以壓到一兩秒而不是三秒。

**裝置省電的辦法，是讓插電的那一端反應快到裝置不必等。**

## 10. 尚未決定、需要實測才能填的數字

**這一節的每一項都還沒有量測值。** 不要把底下的數字當規格，它們是待驗證的起點。

- **廣播逾時分幾段。** 電腦在監聽時應該一兩秒內就連上；手機在背景受 iOS/Android 的背景掃描節流，延遲可能到秒級以上且不可預測。起點：快速路徑 3 秒，延長路徑 30 秒。兩段的界線與長度都要量。
- **手機背景 gateway 到底可不可靠。** iOS 允許背景掃描指定的 service UUID，但會被節流。這決定手機是「備援」還是「不算數」，差別很大。
- **分塊的實際吞吐。** §7 的一秒半是推算的。
- **ESP32-S3 同時擔任 central 與 peripheral 的成本。** 讓一台 ESP32 也能當 gateway 需要這個，但記憶體與排程開銷未知。
- **廣播與掃描的實際功耗。** §3 與 §9 引用的都是一般公開數據，不是本 workspace 任何一塊板子的量測。§9 的整張成本表建立在這些數字上，**如果它們錯了，那一節的結論也跟著錯**——那是這份文件裡最需要先量的一項。
- **Wi-Fi 單 channel scan 到底多快。** §9 說 100–200 ms，是推算。

## 11. 實作分工

**裝置端**：ESP-IDF component，放在這個 workspace 底下，任何板子以 `EXTRA_COMPONENT_DIRS` 引用。對呼叫端只暴露一個像 `esp_http_client` 的介面——呼叫端不知道也不需要知道這次走的是 Wi-Fi 還是 BLE。

**gateway 端**：另外開 project。至少要有電腦端（macOS／Linux／Windows），手機端視 §9 的實測結果再決定。

**選路**：見 §9。BLE 先問，Wi-Fi 後備。Wi-Fi 的可用性一律用 scan 判斷，**不是**用關聯逾時去等——那要十幾秒，而且每一次找不到都得付。

**協議版本相容**：`version` 欄位在廣播的第一個位元組。gateway 看到不認得的版本，應當不回應，而不是猜。
